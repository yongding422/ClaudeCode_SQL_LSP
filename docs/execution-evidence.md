# Transaction and local table evidence

This local follow-up adds structured observations to the shared Core report consumed by MCP. It does not execute SQL, solve a full CFG, evaluate dynamic strings or establish runtime table contents. Observations remain bounded to 64 per module with visible truncation; execution observations receive at most half of that budget so existing sequence/SELECT/external/JSON observations retain space.

`TransactionContract` records syntactic BEGIN TRAN, COMMIT, ROLLBACK and atomic-block counts. `CallerDependent` means the completely parsed body has no explicit BEGIN TRAN/atomic block; it does not mean autocommit. Separate statement commits require an autocommit caller without an enclosing transaction. `ExplicitStatements` does not prove balance or outcomes. A native atomic block can use a savepoint inside an existing transaction; a successful block need not commit its caller's transaction. SNAPSHOT can see the transaction's own updates. Parse errors prevent an absence claim (`Unknown`, `syntaxComplete=false`). Counts describe visited source syntax, not observed operations.

`DeclaredExecutionOptions` retains each original procedure option with an exact source preview, span and preview-truncation flag, including NATIVE_COMPILATION, SCHEMABINDING and EXECUTE AS. `AtomicOption` retains options such as the stated isolation and language. Declared EXECUTE AS is not proof of effective caller authorization. ScriptDOM's EXECUTE-AS option span stops at EXECUTE; a bounded three-token scan recovers the source extent, including quoted principals/comments. If it cannot, the preview is explicitly truncated.

`LocalTableTransfer` records supported INSERT, INSERT EXEC and SELECT INTO target syntax when the local table binding is verified. Inputs are relation source spans, not inferred row/column lineage. `LocalTableRead` links a scalar assignment to local tables appearing in its query. Each input labels whether it is a verified local temp/table variable or only relation syntax. A dropped, ambiguous or persistent relation does not gain a local binding. Inputs are bounded to 16 with an explicit completeness flag. These are source dependencies, not proof of which insert supplied a value or how many rows arrived.

`DynamicSqlConstruction` shows an expression assigned to a local variable that appears in EXEC string syntax in the same module. It is not a reaching-definition proof: branches, reassignments and execution remain unknown. `DynamicExecution` preserves the EXEC-text source span without parsing or executing that string; literal EXEC text previews are omitted. Compact and brief observation expressions respect the requested literal focus, with `expressionOmitted` marking excluded previews. A literal INSERT into a temp table is not counted as a verified static write; an actual later scalar read of the temp table can still be reported separately. Text only assigned/printed without EXEC is not classified as dynamic execution.

Brief facts for sequence allocation, THROW, local transfers/reads and dynamic execution include bounded `sourceOrder` regions with citations and predicates. `beforeFirstExplicitBegin` compares source positions only. TRY/CATCH, branch and loop membership is lexical, with explicit missing-region and truncation indicators; GOTO, conditional execution and runtime error routing are not solved. Full/compact retained reports keep all selected observations; compact input/option spans use the shared evidence table.

`UpdateFrom` preserves UPDATE target, FROM/join, optional WHERE and up to eight assignment previews with exact source spans, preview truncation and assignment/syntax completeness. `wherePresent=false` is only absence of parsed syntax; parse recovery prevents a reliable absence claim. The compact report exposes clause evidence references, and the brief includes selected previews. Focus selection can omit these expressions explicitly. No match uniqueness, row count, summed compound increment or successful outcome is inferred. Multiple matching source rows do not make UPDATE equivalent to SUM. SELECT no-match guidance also distinguishes a fresh NULL scalar from a previously initialized value.

The report presents evidence for the benchmark's transaction and temporary-table gaps. It does not establish that a model will use it correctly. Fresh model comparisons and independent developer acceptance remain separate validation.

[Executable claim checks](evaluation/claim-verification.md) provide small known-input SQL counterexamples in the test-owned disposable server. They let maintainers verify technical claims without asking a developer to certify unfamiliar sample business logic. Model answer review and actual user acceptance remain separate observations.
